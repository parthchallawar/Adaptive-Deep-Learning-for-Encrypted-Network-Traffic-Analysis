Encrypted traffic, read by its rhythm

Name the app before the flow has finished.

The model watches only packet sizes, timing and direction. After every packet it makes one of three calls: name the application, flag the flow as unknown, or wait for one more packet.

Encryption hides the words. The rhythm stays visible.

TLS and QUIC hide every byte of content. What still shows is the shape of the conversation: how big each packet is, which way it travels, and how long the gap is before the next one. Different apps leave different shapes.

The model reads four numbers per packet, for at most the first 30 packets that carry data. It never sees payload, addresses or ports, so it cannot cheat by recognising a server.

Three calls, made after every packet

Each new packet updates two scores. One says how likely the current guess is to be right. The other says how unlike anything from training this flow looks. Drag through the packets to see the rule fire.

Unknown score

  1. Flag as unknown

    From packet 3 on, if the unknown score passes its threshold for this packet count. The threshold is set so about 2% of familiar flows trip it.

  2. Name the app

    From packet 2 on, if the calibrated chance that the current guess is right passes the commit threshold.

  3. Read one more packet

    Otherwise. At the last packet the flow is decided anyway, so nothing waits forever.

How the research was built

Six phases, each closed with its own results document before the next began. Numbers below are from those documents.

  1. 1

    A data pipeline that cannot leak

    12.5 million flows from 42 weeks of CESNET-TLS-Year22, split by time, with four leakage checks enforced every time a split loads.

  2. 2

    Baselines on rented GPUs

    A CNN and a GRU trained on Kaggle with resumable sessions and every run tracked.

  3. 3

    A transformer that reads prefixes

    Self-supervised pretraining, then training at every prefix length. 24 models, about 20 GPU-hours.

  4. 4

    Stop, reject, and hold a budget

    The three-way rule, the unknown score and a feedback controller for packets read per flow.

  5. 5

    Eighteen weeks of drift

    Measured how every model decays over time and which label-free signals see it coming.

  6. 6

    The live system

    This service, its database and the console: the same code as the offline experiments, streamed packet by packet.

One small model, four answers per packet

The transformer was first pretrained to predict the next packet of unlabelled traffic, then taught to classify at every prefix length at once.

  • Unknown score. Combines the model's energy, the distance of its fingerprint from every known app, and how surprised it is by each new packet.
  • Calibrated confidence. Fitted separately for each packet count, so a 0.93 means the same thing at packet 2 as at packet 20.
  • Budget controller. A feedback loop moves the commit threshold so the average number of packets read stays where an operator sets it.
  • Drift monitor. Six label-free signals over windows of 5,000 decisions, each watched by a CUSUM alarm.

Where it goes next

Each of these is written up in the project's future-work notes with what it would take. None is claimed here.

  • Adapting without labels

    The drift monitor sees decay coming. The next step is acting on it: refreshing calibration and thresholds from unlabelled traffic.

  • Ten times the packet rate

    Batched per-flow caches instead of recomputing each prefix, plus int8 and ONNX export.

  • Live capture

    Reading a network interface directly instead of replayed weeks and uploaded captures.

  • Thresholds with guarantees

    Conformal methods so the false-alarm rate holds with a stated probability, not just on average.

  • Decisions across a host's flows

    One device opens many connections; reading them together should decide sooner.
